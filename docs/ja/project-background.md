# プロジェクト背景

このドキュメントでは、Task & Habit Tracker プロジェクトの開発動機、学習目標、技術選定の理由について説明します。

## 開発動機

このプロジェクトは、**モダンなWeb開発のベストプラクティスを実践的に学ぶ**ことを目的としています。

### なぜ実践的なプロジェクトが必要か

- **理論だけでは不十分**: チュートリアルやドキュメントを読むだけでは、実際の開発で直面する課題を理解できない
- **意思決定の経験**: 技術選定、アーキテクチャ設計、トレードオフの判断を経験する
- **ポートフォリオとしての価値**: 完成度の高いプロジェクトは、スキルの証明となる
- **継続的な改善**: 段階的に機能を追加することで、保守性や拡張性を考慮した設計を学ぶ

## 技術スタック選定の理由

### なぜ Java + Spring Boot？

1. **業界標準**: エンタープライズ開発で広く使用されている
2. **エコシステム**: 豊富なライブラリとコミュニティサポート
3. **堅牢性**: 型安全、テスト容易性、保守性に優れる
4. **キャリア価値**: 多くの企業で求められるスキルセット

### なぜ PostgreSQL？

1. **オープンソース**: 無料で使用可能、活発なコミュニティ
2. **機能性**: JSON、フルテキスト検索など高度な機能
3. **信頼性**: ACID準拠、データ整合性の保証
4. **スケーラビリティ**: 小規模から大規模まで対応可能

### なぜ React + TypeScript？

1. **コンポーネント指向**: 再利用可能なUI構築
2. **型安全**: TypeScriptによるコンパイル時エラー検出
3. **エコシステム**: 豊富なライブラリとツール
4. **市場需要**: フロントエンド開発で最も求められるスキル

### なぜ Docker？

1. **環境の一貫性**: 開発・本番環境の差異を解消
2. **依存関係の分離**: クリーンな開発環境
3. **学習価値**: 現代の開発では必須のスキル
4. **デプロイ準備**: 将来のクラウドデプロイに備える

## なぜ Task & Habit Tracker を選んだか

### プロジェクトとしての適切さ

1. **適度な複雑さ**
   - シンプルすぎない（CRUD以上の機能）
   - 複雑すぎない（一人で完成可能なスコープ）
   - 段階的に機能を追加できる

2. **多様な技術要素**
   - 認証・認可（JWT）
   - CRUD操作
   - データ可視化（カレンダー、ヒートマップ）
   - リアルタイム機能（通知）
   - 外部API連携

3. **実用性**
   - 自分でも使いたいアプリケーション
   - 機能の優先順位付けが直感的
   - ユーザー視点での改善がしやすい

4. **拡張の余地**
   - チーム機能
   - モバイル対応
   - AI機能（習慣の提案など）

## 段階的開発戦略

### なぜ段階的アプローチか

1. **早期に成果物を得る**: MVPを早期に完成させ、動くものを確認
2. **フィードバックサイクル**: 各フェーズで学びを次に活かす
3. **スコープ管理**: 機能クリープを防ぎ、優先度の高い機能に集中
4. **モチベーション維持**: 小さな成功を積み重ねる

### フェーズ概要

```
┌─────────────────────────────────────────────────────────────┐
│  Phase 1: MVP (1-2週間)                                     │
│  • ユーザー登録・ログイン                                    │
│  • タスクCRUD                                               │
│  • 基本的なUIレイアウト                                      │
├─────────────────────────────────────────────────────────────┤
│  Phase 2: 機能拡張 (+1-2週間)                               │
│  • 習慣トラッキング                                          │
│  • カレンダー表示                                           │
│  • カテゴリ・タグ                                           │
├─────────────────────────────────────────────────────────────┤
│  Phase 3: 高度な機能                                        │
│  • 外部API連携                                              │
│  • 通知機能                                                 │
│  • チーム機能                                               │
└─────────────────────────────────────────────────────────────┘
```

詳細なフェーズ計画は [features-roadmap.md](./features-roadmap.md) を参照してください。

## 品質維持方針

### なぜ品質を重視するか

**即時の公開予定がなくても、プロダクションレディな品質を維持する**理由：

1. **良い習慣の形成**: 最初から品質を意識することで、良い開発習慣が身につく
2. **技術的負債の回避**: 「後で直す」は往々にして「永遠に直さない」になる
3. **ポートフォリオとしての価値**: 高品質なコードはスキルの証明になる
4. **将来の公開に備える**: 公開を決めた時にすぐに対応できる状態を維持

### 品質基準

| 領域 | 基準 |
|------|------|
| **コード品質** | リンター、フォーマッター、コードレビュー |
| **テスト** | 重要機能のテストカバレッジ確保 |
| **ドキュメント** | コードと同期したドキュメント維持 |
| **セキュリティ** | 依存関係の脆弱性チェック、シークレット管理 |

詳細なガイドラインは [development-guideline.md](./development-guideline.md) を参照してください。
